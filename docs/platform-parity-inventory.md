# Send, thanks feature parity

Send, thanks is an independent mail platform. It must not call the external mail API or require a external mail API key. This checklist tracks behavior, not visual resemblance. Statuses describe the current source tree and are updated as each feature is implemented and verified.

## Core sending and deliverability

| Feature | Status | Notes |
| --- | --- | --- |
| REST email send, get and paginated list | Implemented, local smoke validation passed | SMTP handoff; message list and detail are scoped to the authenticated API key. Detail includes retained text and HTML. Delivery status means relay acceptance, not recipient delivery. No retention windows or self-service message deletion yet. |
| HTML-only sending and plain-text fallback | Implemented, unit tests passed | When plain text is omitted, the app derives a readable text part from HTML for direct, scheduled, broadcast and automation sends. An explicit empty string keeps the text part empty. |
| To, Cc, Bcc, reply-to, headers and tags | Implemented, local validation passed | Stored as message metadata; relay behavior depends on the SMTP server. |
| Base64 attachments | Implemented, local validation passed | Request limit is 1 MB; attachments capped at 650 KB total and 10 files per message. Attachment bytes are not retained. |
| Reusable templates with variables | Implemented, local smoke validation passed | Draft and published versions, immutable version history, aliases, fallback values, duplicate/publish operations, HTML escaping, a visual block editor with sandboxed preview, and protection against deleting templates referenced by automations. Nested template folders support creation, movement, and deletion; deleting a folder and its subfolders returns their templates to All templates. Link validation runs before publication or sending. Per-workspace isolation is not implemented. |
| Broadcast folders | Implemented, local tests passed | Nested folders support create, rename, move, filter and search. Deleting a folder subtree returns its campaigns to All campaigns without deleting campaign records. Folder management is account-wide in the single-admin app; workspace isolation is absent. |
| Email link checker | Partial, unit tests passed | Static checks run before API sends, broadcast queuing, template publication, and automation handoff. It detects missing or empty destinations, unsafe schemes, malformed URLs and common placeholders; dynamic variables are checked after rendering. It does not warn inline while editing or fetch remote pages to confirm that a destination responds. |
| Email client compatibility checker | Partial, unit tests passed | Template and broadcast HTML source editors show advisory findings while editing for commonly stripped elements, event handlers, linked stylesheets, modern CSS layout and color features, and framework markup. Checks are a fixed heuristic list, not a refreshed client-support matrix; they do not annotate code or guarantee rendering across inboxes. |
| Batch send | Implemented, local smoke validation passed | Accepts the standard direct JSON array and the earlier `{ "emails": [...] }` wrapper. Up to 100 messages count as one API request, five SMTP sends run in parallel, and each item has its own result and idempotency key. Authenticated API responses expose `ratelimit-limit`, `ratelimit-remaining`, and `ratelimit-reset`; denied requests add `retry-after`. The single workspace shares a fixed 10-requests-per-second window across API keys. Each send is synchronous and can exceed a serverless execution window. |
| Scheduled sends and retry queue | Implemented, local worker smoke validation passed; production activation pending | Durable database records, reschedule/cancel endpoints, three total attempts and a protected worker. Requires `CRON_SECRET`, durable database storage, a production deployment, and a Vercel plan that meets the desired cadence. |
| Domain verification and authentication guidance | Partial | Send, thanks TXT ownership checks and read-only SPF, DMARC and MX diagnostics are available. DKIM, custom return paths and custom tracking domains still rely on the selected relay or manual DNS configuration. |
| Open and click tracking | Implemented, local smoke validation passed | Optional per-domain tracking, signed pixels and redirects, event API and aggregate dashboard counts. Custom tracking domains are not implemented. Open counts are approximate because clients can block or prefetch images. |
| Delivery, bounce and complaint events | Partial, local signature and parser tests passed | A signed delivery-notification endpoint validates envelopes, deduplicates events, links outcomes to saved relay message IDs, advances message status without downgrades, and adds permanent bounces and complaints to the workspace suppression list. A compatible event source is not configured or production verified. |
| Webhook endpoints, signatures, retry and replay | Partial, local smoke validation passed | API and dashboard CRUD, per-key event filters, event/attempt history, one-time signing secrets with rotation, HMAC signatures, bounded retry and replay are implemented. Targets must be public HTTPS endpoints; private and loopback addresses are rejected. Events cover email scheduling, relay handoff failures/acceptance, tracking, API contact lifecycle, source-key scoped contact updates and topic changes from signed public preference pages, domain creation/verification/settings/deletion, and recipient-specific `email.delivered`, `email.delivery_delayed`, `email.bounced` and `email.complained` outcomes when signed delivery notifications are configured. Preference mutations and their webhook deliveries are committed in one database transaction; event IDs remain stable across retries. Production delivery still depends on a durable database, `EMAILGO_WEBHOOK_SECRET`, `CRON_SECRET`, and a running worker. |
| Suppression management | Partial, local smoke validation passed | Workspace-scoped manual suppression lists support API/dashboard add, get, paginated list, remove, batch import/remove, dashboard CSV import/export, and `suppression.added`, `suppression.removed`, and `email.suppressed` webhook events. Transactional recipients are filtered from To/Cc/Bcc and scheduled/broadcast messages recheck the owning workspace list before relay handoff. Permanent bounce and complaint events are assigned to the workspace owning the matched message when a compatible delivery source is configured; automatic provider-wide syncing is absent. Signed global unsubscribe and topic preferences remain separate and include RFC 8058 one-click handling for broadcasts. |
| Usage metrics and request logs | Partial, local smoke validation passed | Email metrics and API request log list/detail endpoints are implemented, with API-key scoping and bounded result sets. Signed delivery notifications add delivered, delayed, bounced, bounce subtypes and complained counts; these outcomes remain empty until an event source is configured. Derived rates are available as decimal fractions. Global unsubscribes are attributed to broadcasts sent with the newer per-message preference links; older links and manual contact changes have no source-email attribution. Dashboard message history supports server-side search, status filters, cursor pagination and sandboxed HTML preview. |

## Workspace and growth tools

| Feature | Status | Notes |
| --- | --- | --- |
| Contacts, properties, tags and consent state | Partial, local smoke validation passed | API/dashboard CRUD and CSV record unknown consent by default, with opt-in source and time fields. The dashboard supports selecting and permanently deleting up to 120 contacts per action after typing a confirmation phrase; full-access API keys can also delete one contact at a time. Unsubscribe remains suppressive. Signed public preference pages support topic choices and global unsubscribe. |
| Contact property definitions and fallbacks | Partial, local checks passed | Typed string/number definitions, per-property fallback values, dashboard, API, SDK and CLI support. The dashboard supports confirmed bulk deletion of up to 120 definitions; saved values on contacts remain unchanged. Definitions, fallback lookup, CRUD, and import conflict detection are scoped to the owning workspace; existing definitions backfill to the default workspace. API contact imports create missing string and number definitions in the same database transaction as imported rows and reject type conflicts. Dashboard property suggestions and automatic boolean definitions remain absent. Broadcast rendering applies workspace property defaults when a contact value is missing or null and supports per-tag fallback syntax in subject, text and HTML. |
| Audiences, segments and topics | Partial, local filter tests passed | Saved live segments support legacy tag, consent and unsubscribe filters plus grouped tag, consent, unsubscribe, typed string/number contact-property, and recent email activity conditions for sent, delivered, opened, clicked, bounced and complained events. Groups and their rules can each match all or any. Counts, paginated contact previews, and point-in-time `all_contacts`, `subscribers` and `unsubscribers` metrics use the same predicate as campaign recipient selection. Topic CRUD, a public signed preference center, contact topic preferences, and multipart contact imports with column mapping, conflict handling, segment assignment, and explicit-consent topic opt-in are available. API imports create missing mapped string and number property definitions atomically. Imports are synchronous, limited to 2 MB and 2,000 rows. Nested Boolean expressions, multiple independent workspaces, and full import job tracking remain absent. |
| Broadcasts/newsletters | Partial, local checks passed | Dashboard can save, edit, schedule, cancel and queue personalized campaigns to saved segments or subscribed topics. Nested campaign folders support organizing drafts. Full-access API keys can duplicate any owned campaign, including sent campaigns, into a draft with the audience, sender, subject, reply-to, preview text and content retained; the `(copy)` name is capped at 70 characters. The API accepts reply-to and preview text on draft create/update, and the dashboard composer exposes both optional fields after Subject with inline validation before save or queue. Preview text is inserted as an escaped hidden preheader when HTML content exists; text-only messages use their body snippet. The create, direct queue, and reschedule APIs accept ISO 8601 timestamps and supported natural times such as `in 5 minutes`, `tomorrow at 9am`, and `Friday at 3pm ET`; calendar expressions without a zone use UTC and schedules remain limited to 30 days. Personalization includes contact first and last names, email, custom properties, preference links and explicit per-tag fallbacks. Only opted-in, non-suppressed contacts are eligible. Messages include signed preferences links and RFC 8058 unsubscribe headers. Each send is limited to 1,000 recipients and is drained by the existing worker. Recipient and clicked-link analytics are available through key-scoped, bounded APIs; recipient outcomes require a configured signed delivery source. Broadcast drafts include the visual block editor and sandboxed preview. Experiments and production relay verification are absent. |
| Automations | Partial, local smoke and canvas persistence tests passed | Full-access API and dashboard create, activate, pause and archive event-triggered workflows. Supports condition branches, delays up to 30 days, filtered wait-for-event, template email, contact name/property/tag updates, add-to-segment, idempotent custom event sends and per-step run history/cancel. Event schema CRUD and payload validation are implemented. Template references are protected from deletion. The dashboard has a visual graph canvas with keyboard insertion, branch connection and reordering, draft-only save, explicit activation confirmation, and persisted canvas offsets. Drag-and-drop gestures are absent. A durable database and scheduled worker are required. Contact deletion actions and retry/resume for failed runs are absent. |
| Inbound email and message receiving | Partial | A signed, replay-resistant normalized event bridge stores inbound message bodies and attachments. The dashboard groups messages by `Message-ID`, `In-Reply-To` and `References`, and can list, retrieve and download them. A received message and its subscribed webhook delivery are stored atomically, and duplicate source events can restore a missing delivery by stable event identity. Actual receipt still depends on a separately configured forwarding service; Send, thanks does not host inbound SMTP or configure MX records. |
| Shared inboxes | Partial, parser and SQLite search tests passed | The single-admin dashboard supports inbox selection, conversation search, Inbox/Sent/Archive/Spam/Trash folders, labels, read state, and threaded plain-text replies. Search accepts Gmail-like `from:`, `to:`, `subject:`, `before:YYYY-MM-DD`, `after:YYYY-MM-DD`, and `is:read`/`is:unread` filters, quoted phrases, and plain-text terms; result, total, unread, and cursor checks share the same parsed predicate. Reply, reply-all, and forward modes use a persisted per-thread draft, autosave, explicit discard, Cc/Bcc, selected sender from a verified domain, and idempotent sends. Reply-all excludes the inbox address and duplicate recipients. Forward includes the latest received message as quoted plain text; original attachments are not forwarded. No inbox address provisioning, assignment, private notes, team access, agent actions or inbox workflows are implemented. |

## Developer and team platform

| Feature | Status | Notes |
| --- | --- | --- |
| API keys and REST reference | Partial, local smoke validation passed | Keys are stored as hashes. Full-access and domain-restricted sending-only keys are implemented. Full-access keys can list, create, inspect, rename and revoke keys through `/api/v1/api-keys`; these management operations are scoped to the workspace attached to the authenticating key. Raw key material is returned only at creation. An OpenAPI 3.1 document is served at `/api/v1/openapi.json`. API key scopes remain coarse and OAuth is absent. |
| Domain management API | Partial | Full-access keys can list, create, inspect, verify, update tracking settings and delete unused sender domains through `/api/v1/domains`; each operation is scoped to the workspace attached to the authenticating key. Domain names are unique within a workspace. DNS checks cover ownership, SPF, DMARC and MX; DKIM and return-path setup still come from the SMTP relay. |
| SDK, CLI and MCP tools | Partial, in-process MCP protocol tests passed | A dependency-free source Node SDK and repository CLI cover implemented Send, thanks API methods, including automation/event methods. The local stdio MCP server exposes the principal email, domain, contact/import, segment, topic, template, broadcast, automation, event, webhook, suppression, usage, log, CSV export, and inbound attachment operations. Attachment content is capped at 4 MiB. It redacts provider names and secret material, and requires explicit confirmation fields for destructive operations and campaign sends. It omits API-key management, bearer share links, webhook secret rotation, remote MCP hosting, published SDKs, keychain-backed CLI profiles, and a local webhook tunnel. |
| API rate limits | Implemented, isolated SQLite and local production HTTP smoke passed | Authenticated API requests and threaded inbox replies share a fixed 10-request-per-second window by workspace. API keys in the same workspace share that workspace's limit. Batch sends count as one API request. Responses expose limit, remaining, reset-in-seconds, and retry-after on 429. Requests without a valid API key are not counted. Higher per-workspace overrides are not implemented. |
| CSV data exports | Partial, local tests passed | Full-access API keys can stream filtered CSV for outbound and received email metadata, broadcasts, contacts, domains, request logs, and API key metadata. Key-owned messages and broadcasts are scoped to the authenticated key; contacts, request logs, domains, and API-key metadata are scoped to its workspace. Message bodies, attachments, log bodies, verification tokens, and API key secrets are excluded. Formula-like cells are escaped. The Node SDK and CLI can download the CSV. Exports are synchronous streams without a durable exports page, job status, or expiring download links. |
| Multiple workspaces, members and roles | Partial, gated foundation | Existing API keys, sender domains, contacts, saved segments, topics, contact property definitions and suppressions are backfilled to a default workspace. API-key, sender-domain, property-definition and suppression management use workspace-scoped queries. Contact CRUD, CSV import, property definition and fallback lookup, block-list checks for direct, scheduled, automation, inbox-reply and broadcast sends, segment list/item/metrics, segment membership, topic list/item/subscription/preferences/import, event targeting, import assignment, automation segment actions, and campaign audience resolution use the authenticated key's workspace. Contact addresses, segment names, topic names/slugs, property keys and suppression addresses may be reused in separate workspaces. Creating or switching workspaces, membership, invitations, and workspace-aware admin sessions remain unavailable. Messages, campaigns, templates, automations, webhooks, import history, exports, and background workers are not fully workspace-isolated; do not treat the app as safe for general multi-workspace use yet. |
| OAuth, SSO and audit log | Not implemented | Requires identity and account-security design. |
| Billing, quotas and plan controls | Not implemented | No billing provider or usage enforcement exists. |
| Agent inboxes and inbox automation | Not implemented | Send, thanks has no inbox agent connection, assignment, draft/forward action, instruction controls or inbox-triggered workflow. |

Webhook signatures use `svix-id`, `svix-timestamp`, and `svix-signature` headers. The `whsec_` value is base64url encoded HMAC material. The receiver signs/verifies `<event_id>.<timestamp>.<raw_json_body>` using HMAC SHA-256. Delivery payloads remain in the database for retries; bounded receiver response excerpts are retained in attempt history.

## Verification notes

Current product capability notes were checked against primary product documentation on 27 November 2026. Source names and URLs are omitted from this public inventory so customer-facing material does not expose other mail service names. The worker scheduling reference remains [Vercel Cron Jobs](https://vercel.com/docs/cron-jobs).

Do not describe Send, thanks as a complete email platform until every applicable row has implemented behavior and verification evidence. Features requiring a delivery event provider, inbound mail provider, team identity system or worker must remain listed as dependencies until configured.
